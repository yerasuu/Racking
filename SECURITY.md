# Security

Racking is meant for a trusted local network: one service, one Bearer token per agent, no TLS. Do not expose it to the internet. The server runs on Unix (Linux); the `rack` client and `racking-mcp` also run on Windows.

## What it protects

- **Who can connect.** Before reading a token, the server checks the client address against `allow_from` (loopback and the private and link-local ranges by default) and refuses any other with 403. The client is the TCP peer; `X-Forwarded-For` is read only when the peer is in `trusted_proxies` (empty by default), walked from the right so a value the client wrote itself is never used ([protocol: LAN only](docs/protocol.md#lan-only)). Set `trusted_proxies` only when a reverse proxy is the sole way in: if clients can also reach the port directly, one inside a trusted range can claim any address. The server refuses to bind a public or wildcard address (`0.0.0.0`) unless the config says `allow_public_bind = true`, and then warns at every start.
- **Who joins.** A new agent gets its token only by redeeming a one-time pairing code an admin agent asked for (`rack link`), and the token does nothing until a person at the inviter's terminal has compared a four-word fingerprint with the joiner's screen and typed `y` (`rack join` on the other side). The code is 16 symbols from the OS random source (79.3 bits), single use, valid 10 minutes by default, stored only as a salted SHA-256, and never logged or audited. Unknown, used, expired and voided codes get one and the same answer; five wrong codes void every open invite and lock the sender's address out for 15 minutes. The confirmation question is read from the terminal, not stdin, so a script or an agent cannot answer it; `--yes-if-fingerprint` exists for tests only. Agents made this way reach only the agents they are linked with, and an admin can remove a link, which revokes the joiner's token.
- **Who is who.** Every route except `GET /`, `GET /help` and `POST /join` (which takes a pairing code instead) needs a token. File tokens live in the server config (keep it private); tokens made with the admin API are 32 bytes from `/dev/urandom`, shown once and stored only as their SHA-256. All are compared by digest in constant time. Rotating or removing an API agent takes effect on the next request, without a restart. Answers that carry a token are never kept for idempotent replays.
- **Who may tell whom what.** The server gives each agent a role from its config: one `main` (the agent the owner talks to) and `worker`s. A job's `from_role` comes from the server, never from the request, so no message can claim the owner's authority. With roles set, a worker may start jobs only for the main agent unless `[permissions]` says otherwise. Only a job with `from_role: main` may carry delegated authority, and what a worker does with it is its local policy's call (below); everything else is data.
- **What a worker runs on its own.** A worker's local policy (`rack policy`, `~/.config/rack/policy.toml`, mode 600, edited only by that machine's owner, never read from a work directory or a job) lists profiles: exact commands with anchored argument patterns, read and write paths, network hosts, variables and limits. `rack policy decide` lets a task start a profile only when its server-set `from_role` is `main`, it names an enabled profile in its `profile` field (which the server accepts only from the main agent; the old first-body-line form counts only on a server without that field), the server is not paused and the hop and open-task limits hold; any error reading the policy denies. In the worker's Claude Code session, the `rack policy hook` `PreToolUse` hook denies every tool call outside the active profile: Bash commands are read as a plain argv and any shell syntax is refused, paths are resolved (no `..`, symlinks followed) before they are compared. A profile may not write the policy, the config directory or a command it runs. Every decision goes to a local audit log.
- **Runaway agents.** Chains of tasks answered with tasks stop at 3 hops, open tasks per sender and recipient and jobs per sender per minute are capped, and the owner's emergency brake (`POST /admin/pause`) stops workers from sending while still delivering, so every agent learns it should stop.
- **Disk exhaustion.** Every file counts against its sender's quota (`[quota] per_agent_bytes`, 8 GiB by default: the attachments of the jobs it sent plus its open uploads, until the jobs are purged), and a new upload is refused with 507 while the data directory's file system would fall under `disk_free_min_bytes` (1 GiB). Upload sizes are capped per file, per chunk and per job, an upload session idle for 24 h is dropped with its data, and the hourly purge deletes files no row points to. The free space comes from POSIX `df`; where it cannot be read, the reserve is not checked (the server logs it once) and only the quotas bound the disk. Uploads running at the same time are each checked against the free space alone, so many large ones started together can overshoot the reserve by their sum. A broadcast stores one copy per recipient.
- **Received archives.** `rack get-attachment JOB NAME.tar --extract DIR` treats the archive as hostile: it reads POSIX ustar only (pax and GNU extensions are refused), checks every entry before writing anything, and refuses links, devices and FIFOs, absolute names, `..`, backslashes, colons, NUL bytes, Windows device names, duplicates (also by case), entries that would land on a symlink, on an existing file (unless `--overwrite`, which removes the file first instead of writing through it) or outside `DIR`, a truncated archive, and more than `--max-bytes` (4 GiB) or `--max-files` (100000). Directories are created one level at a time without following symlinks; files get mode 644 or 755, never setuid or setgid. `rack attach JOB DIR` packs only regular files and directories and skips symlinks with a warning, so a link to a secret outside the folder never travels. `racking_get_attachment` never unpacks.
- **Who reads the past.** `GET /threads/{id}` and `GET /jobs` (search) show only jobs the caller sent or received, so bodies are searchable by their two participants only; a job of a thread between other agents is counted, never shown. Both are read-only peeks that deliver nothing.
- **Accountability.** Admin actions, refused admin calls, joins, wrong pairing codes (with the peer address) and link changes go to an audit table (who, what, target, result), never bodies, codes or tokens.
- `rack update` checks a sha256 only. A compromised service or admin token can serve a bad binary (see the decision on update distribution in the project board notes).

## What it does not protect

- **No TLS.** On the LAN, tokens, pairing codes and job contents travel in clear; anyone who can sniff the network can read them and replay a token. Use a network you trust, or a tunnel (WireGuard, SSH) you set up yourself.
- **Code interception.** Someone who reads a pairing code (off a screen, a chat, or the LAN) can redeem it before the intended machine does. That is why the fingerprint check is mandatory and never skipped: their name and token give other words than the joiner's screen shows, and the real joiner gets `bad_code`, so a careful inviter denies them. The check protects the pairing only: someone who can watch the LAN later can still read the token as it travels in clear (above). An inviter who confirms without comparing the words gives the agent to whoever redeemed the code.
- **Agents of the config file are linked with everyone**, as before links existed, so links constrain only agents made through the API. `racking-server invite` needs no token: it opens the database directly, so it works for whoever can read and write the data directory, who controls the server anyway (below).
- **A stolen token is that agent** until it is rotated or removed from the config. A stolen admin token can create agents, read the audit log, pause the server and publish `rack` binaries. A stolen main token carries the owner's authority as far as the workers' local policies allow.
- **`allow_from` trusts the network.** Any host inside the allowed ranges can try tokens; a spoofed source address on the LAN is not detected. Behind a proxy or NAT, every client behind it has the same address, so `allow_from` and the `/join` lockout cannot tell them apart.
- **Slow clients.** tiny_http 0.12, the HTTP layer, sets no read or write timeout on its connections and offers none to configure, so a client that sends slowly holds a request thread. At most 64 requests are served at once (more get `429`), which bounds the damage to that; through Traefik, its `readTimeout`, `writeTimeout` and `idleTimeout` cut slow clients before they reach the server ([deploy: Behind Traefik](docs/deploy.md#behind-traefik-tls)).
- **Content is never checked.** Bodies, titles, attachments, `about` lines and capabilities are whatever the sender wrote. The roles decide who sent a job, not whether what it says is true or safe; a main agent can still be fooled by data it read and pass it on.
- **`parent` is voluntary.** A sender that leaves it out starts a new chain, so the depth limit stops honest loops, not a hostile agent; the per-sender limits and the brake are the backstop.
- **Slow connections.** The server has no per-connection read timeout, so a slowloris client is bounded only by the proxy: the optional Traefik profile sets read, write and idle timeouts for that (see docs/deploy.md).
- **A stop cuts off what is still running after the grace period.** SIGTERM lets requests finish for `shutdown_grace_secs` (default 10 s), then the process exits; an upload cut off then is lost, not resumed.
- **The local policy relies on Claude Code.** The hook and the `permissions` of `rack policy settings` work only while Claude Code runs the hook and honours its answer, the worker's session was started with those settings, and nothing else on the machine acts for the agent. A prompt-injected worker can still misuse everything the active profile allows: a program it may run does what that program does (its own file and network access are not confined; for that, use the OS or Claude Code's sandbox), an argument pattern with `*` takes any text, and `env_allow` values are not checked. Keep profiles minimal, prefer fixed arguments, and keep the commands they run outside any path they may write. On Windows the file's permissions are not checked; protect it with its ACL.
- **The server host.** Whoever controls the machine, its config file or its database controls Racking. The database holds token hashes, jobs and attachments in clear.

## Optional Traefik profile

Internet exposure goes only through Traefik with TLS. The proxy has no Docker socket: routes come from a read-only file (`config/traefik-dynamic.yml`), so an attacker who compromises Traefik does not get the Docker API and, through it, the host (the risk the [Traefik docs describe](https://doc.traefik.io/traefik/v3.6/reference/install-configuration/providers/docker/) for the Docker provider). Traefik still holds the TLS private key and sees all traffic in clear. In this mode the server is not published on the host; only Traefik reaches it.

Report a vulnerability privately through GitHub: [Security advisories](https://github.com/yerasuu/Racking/security/advisories/new). Please do not open a public issue for it.
