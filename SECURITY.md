# Security

Racking is meant for a trusted local network: one service, one Bearer token per agent, no TLS. Do not expose it to the internet. The server runs on Unix (Linux); the `rack` client and `racking-mcp` also run on Windows.

## What it protects

- **Who can connect.** Before reading a token, the server checks the TCP peer address against `allow_from` (loopback and the private and link-local ranges by default) and refuses any other with 403. `X-Forwarded-For` is ignored; behind a reverse proxy the peer is the proxy, so filter there too; per-IP limits count the proxy as one client (a later change will honour `X-Forwarded-For` from a trusted proxy). The server refuses to bind a public or wildcard address (`0.0.0.0`) unless the config says `allow_public_bind = true`, and then warns at every start.
- **Who joins.** A new agent gets its token only by redeeming a one-time pairing code an admin agent asked for (`rack link`), and the token does nothing until a person at the inviter's terminal has compared a four-word fingerprint with the joiner's screen and typed `y` (`rack join` on the other side). The code is 16 symbols from the OS random source (79.3 bits), single use, valid 10 minutes by default, stored only as a salted SHA-256, and never logged or audited. Unknown, used, expired and voided codes get one and the same answer; five wrong codes void every open invite and lock the sender's address out for 15 minutes. The confirmation question is read from the terminal, not stdin, so a script or an agent cannot answer it; `--yes-if-fingerprint` exists for tests only. Agents made this way reach only the agents they are linked with, and an admin can remove a link, which revokes the joiner's token.
- **Who is who.** Every route except `GET /`, `GET /help` and `POST /join` (which takes a pairing code instead) needs a token. File tokens live in the server config (keep it private); tokens made with the admin API are 32 bytes from `/dev/urandom`, shown once and stored only as their SHA-256. All are compared by digest in constant time. Rotating or removing an API agent takes effect on the next request, without a restart. Answers that carry a token are never kept for idempotent replays.
- **Who may tell whom what.** The server gives each agent a role from its config: one `main` (the agent the owner talks to) and `worker`s. A job's `from_role` comes from the server, never from the request, so no message can claim the owner's authority. With roles set, a worker may start jobs only for the main agent unless `[permissions]` says otherwise. Only a job with `from_role: main` may carry delegated authority, and what a worker does with it is its local policy's call (a later part of #43); everything else is data.
- **Runaway agents.** Chains of tasks answered with tasks stop at 3 hops, open tasks per sender and recipient and jobs per sender per minute are capped, and the owner's emergency brake (`POST /admin/pause`) stops workers from sending while still delivering, so every agent learns it should stop.
- **Accountability.** Admin actions, refused admin calls, joins, wrong pairing codes (with the peer address) and link changes go to an audit table (who, what, target, result), never bodies, codes or tokens.
- `rack update` checks a sha256 only. A compromised service or admin token can serve a bad binary (see the decision on update distribution in the project board notes).

## What it does not protect

- **No TLS.** On the LAN, tokens, pairing codes and job contents travel in clear; anyone who can sniff the network can read them and replay a token. Use a network you trust, or a tunnel (WireGuard, SSH) you set up yourself.
- **Code interception.** Someone who reads a pairing code (off a screen, a chat, or the LAN) can redeem it before the intended machine does. That is why the fingerprint check is mandatory and never skipped: their name and token give other words than the joiner's screen shows, and the real joiner gets `bad_code`, so a careful inviter denies them. The check protects the pairing only: someone who can watch the LAN later can still read the token as it travels in clear (above). An inviter who confirms without comparing the words gives the agent to whoever redeemed the code.
- **Agents of the config file are linked with everyone**, as before links existed, so links constrain only agents made through the API. `racking-server invite` needs no token: it opens the database directly, so it works for whoever can read and write the data directory, who controls the server anyway (below).
- **A stolen token is that agent** until it is rotated or removed from the config. A stolen admin token can create agents, read the audit log, pause the server and publish `rack` binaries. A stolen main token carries the owner's authority as far as the workers' local policies allow.
- **`allow_from` trusts the network.** Any host inside the allowed ranges can try tokens; a spoofed source address on the LAN is not detected.
- **Content is never checked.** Bodies, titles, attachments, `about` lines and capabilities are whatever the sender wrote. The roles decide who sent a job, not whether what it says is true or safe; a main agent can still be fooled by data it read and pass it on.
- **`parent` is voluntary.** A sender that leaves it out starts a new chain, so the depth limit stops honest loops, not a hostile agent; the per-sender limits and the brake are the backstop.
- **Slow connections.** The server has no per-connection read timeout, so a slowloris client is bounded only by the proxy: the optional Traefik profile sets read, write and idle timeouts for that (see docs/deploy.md).
- **The server host.** Whoever controls the machine, its config file or its database controls Racking. The database holds token hashes, jobs and attachments in clear.

## Optional Traefik profile

Internet exposure goes only through Traefik with TLS. The proxy has no Docker socket: routes come from a read-only file (`config/traefik-dynamic.yml`), so an attacker who compromises Traefik does not get the Docker API and, through it, the host (the risk the [Traefik docs describe](https://doc.traefik.io/traefik/v3.6/reference/install-configuration/providers/docker/) for the Docker provider). Traefik still holds the TLS private key and sees all traffic in clear. In this mode the server is not published on the host; only Traefik reaches it.

Report a vulnerability privately through GitHub: [Security advisories](https://github.com/yerasuu/Racking/security/advisories/new). Please do not open a public issue for it.
